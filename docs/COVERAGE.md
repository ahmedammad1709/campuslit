## Required signed-in validation

1. Inventory URLs and component classes for every reachable student page in both portals. Use sanitized HTML snapshots when possible; exclude credentials, session tokens, enrollment numbers and actual student records.
2. Test Crystal, Midnight, Linen, Grove and Bloom on each page, including extreme custom accent colors, 13/19 px text, compact/spacious spacing and 0/20 px corners.
3. Exercise menus, keyboard navigation, dropdowns, validation errors, pagination, date pickers, uploads, assignment submission, download links, dialogs and ASP.NET postbacks. Verify actions with and without the extension.
4. Check attendance charts and all success/error/warning text remains understandable. Chart canvas and semantic status colors are intentionally not recolored blindly.
5. Check original print/PDF/challan output, mobile widths and zoom. PDF viewer pages and external origins are outside styling scope.
6. Check live switching across CMS and LMS tabs, disabling one portal, global disable, system appearance, reload persistence and extension removal.
7. Check Chrome and Firefox separately, including permission prompts and Firefox signing requirements.

Do not list a page as verified until it has been tested in a real signed-in browser. No credentials should be committed or requested in chat.

## Attendance planner (v0.4)

`attendance.js` (pure maths, no page access) + `cms.js`. Rules: attendance must be MORE than 75% at the end of the semester (exactly 75.0% is not enough); a course's credit hours are its class hours per week; classes are whole hours (1 or 2 h); a lab is one continuous 3-hour session per credit hour. So the semester holds `weeks x weekly hours` (weekly = credit hours, or credit hours x 3 for a lab) and the hours left are that minus the hours held so far. With P attended, T held, S in the semester and R = S - T left: the fewest hours you must still attend is the smallest `a` with `100(P + a) > 75 S`, rounded up to whole classes (whole 3-hour sessions for a lab); "can miss" is the rest, rounded down to whole classes. Everything is in whole minutes. The semester length is a setting (Settings > Portals > Attendance planner, default 16 weeks, 10-20): it is an assumption to set to the real figure. Credit hours come from the Attendance page's table; the dashboard script has none, so there (and wherever they are missing) the planner falls back to counting from now. Labs are recognised by "Lab" in the title or a code like `CSL 220`. Shown on the CMS dashboard (data from the page's own script) and on the Attendance page (columns found by header text, present hours printed as "20.0 :90.91%").
Error handling: each course is built on its own (a bad record is skipped or shown as "Cannot work this out from the numbers on the page"); missing, negative, non-numeric or absurd values, attended > held, and a portal percentage that contradicts its own hours (more than 1 point off) all give that message instead of advice; the script data is extracted with a string-aware bracket walk; the planner waits for the page to finish loading so it never works from half a table; every CMS feature runs in its own try/catch; if the module or the data is missing, the original chart or table is left alone.
Verified: brute force over six credit/lab/length configurations against an independent reference (the promise holds and one more class breaks it), your worked examples (1-credit lab, 21 h held = 7 sessions; 2-credit, 14 h = week 7), messy-input and extraction tests, and in real Chrome on the sample dashboard and Attendance pages (all courses, one corrupted record, live change of semester length, removal when the CMS is switched off). Not verified: the real Attendance page with a different column layout or several semesters, the university's true semester length, and whether every lab is named as such (otherwise a lab is treated as ordinary hours).

## Assignments due-soon card (v0.3)

`deadlines.js` (pure maths, no page access) + `lms.js` + `lms.css`, on the LMS Assignments page only. The portal shows one course at a time (a course dropdown) and the dashboard has no assignment data, so the card covers the selected course; a cross-course view is done by the reminder popup below, from a note kept on the device. The table is found by its header text (Deadline, Title, Added Submission, Action). Each row's deadline is the later of the "Extended" and "Actual" labels, parsed as Pakistan time (UTC+5) whatever the device's time zone is. A row is Submitted when its Added Submission cell has a download link; Closed when the portal's own Action cell says the deadline is exceeded (the portal wins over the device clock, so a wrong clock cannot show a closed assignment as open); otherwise it counts down. If the portal still offers an upload box but the clock says the deadline has passed, it says "Open. Check the deadline on the portal" instead of guessing. Only the presence of upload boxes is looked at, never their contents, file names or link addresses. Nothing is sent. The card follows the table if the page changes it, refreshes every 30 s, and is removed when the LMS is switched off.
Verified: 9 unit tests (date formats incl. 12 am/pm, leap days, junk, non-breaking spaces; boundary at the exact deadline; clock-versus-portal disagreements; messy input), and in real Chrome against the sample page (four rows: submitted, two open, one closed; unreadable dates; table changed and emptied under the card; removal on switch-off), plus light, dark and phone-width screenshots. Not verified: the real page's Action cell for an assignment that is still open (only closed ones were available to inspect: the open-state upload control is assumed), a real submitted-after-deadline case, and other wordings the portal may use for "Deadline Exceeded".

## Assignment reminder popup (v0.3)

`deadlines.js` (remember / upcoming / dismiss, pure) + `lms.js` + `lms.css` + a switch and a "forget" button in Settings > Portals. When the Assignments page is built, the open, unsubmitted assignments of the selected course (title and deadline only, plus the course and semester names the page has selected) replace that course's entry in `chrome.storage.local` under `bahriaStudioReminders`; a course with nothing open is forgotten. On every other logged-in LMS page (top frame only), a popup names the soonest one due within 7 days, with "+N more open this week" and a note when the information is more than an hour old ("Checked on the Assignments page 3 days ago"). The cross dismisses that assignment for 8 hours; if its deadline moves it is a different assignment and the reminder returns. Past deadlines drop out by themselves, and entries unseen for 150 days are deleted. Limits: 40 courses, 60 assignments each, 80 characters per title. A clock that has moved backwards (note saved "in the future") is not trusted. Whatever is read back from storage is validated again; a damaged note shows nothing and is rewritten at the next Assignments visit. Reminders off: nothing is saved and any existing note is deleted; "Reset all settings" deletes it too. The settings-page preview uses invented sample data held in memory and never touches storage. No link addresses, marks, file names or form contents are read or kept.
Verified: 16 unit tests for the logic (replace-per-course, caps, horizon, 8-hour snooze and its expiry, moved deadlines, clock moving back, damaged/hostile stored data including `__proto__` names), and in real Chrome: note written with exactly course/semester/time/title/deadline and no link text, popup on the dashboard (text, urgency colour, link to the portal's own Assignments route), none on the Assignments page, crossed away and still hidden after reload, forget button and its count, preview isolation, reminders off then on, damaged note, removal on LMS switch-off.
Not verified: behaviour on the real portal for an open assignment (see above), and a student who submits from another device (the popup then keeps reminding until they next open the Assignments page; the popup says how old its information is).

## Time table to calendar file (v0.3)

`calendar.js` (pure: events in, `.ics` text out) + `cms.js` (button, panel, download) + `cms.css`, on the CMS Time Table page. The panel asks for the first day of classes (default: this week's Monday), the weeks of classes (default: the semester-length setting) and a reminder (none, 10 or 30 minutes, 1 hour). Each class becomes one weekly repeating event (`RRULE:FREQ=WEEKLY;UNTIL=...;BYDAY=..`) in `TZID=Asia/Karachi` (UTC+5, no daylight saving; the time zone is defined inside the file), starting on the first matching weekday on or after the first day, and stopping at the end of the last week. Titles, rooms and teachers are stripped of control characters and escaped, so a hostile title cannot add lines or properties to the file; lines are folded at 75 octets without splitting multi-byte characters; the file uses CRLF line endings. Event ids are derived from the class (title, weekday, times, room, semester), so importing the file again updates the events instead of duplicating them. Limits: 200 events, 1-30 weeks. The file is built in memory and handed to the browser as a Blob download; nothing is stored or sent. Only the values of the panel's own three controls are read (they have no `name`, so the portal's form never submits them, and Enter is handled by the panel).
Verified: 12 unit tests (exact dates and times, weekday shifts for every start day, end date, 24:00 end, escaping and injection attempts, non-English text and folding at 75 octets, reminders, bad input, stable ids, size cap, file name, default Monday), the downloaded file parsed with a standard calendar library (12 events expand to 144 correct occurrences with the right UTC offset and reminder), and in real Chrome: the file is actually downloaded to disk and read back (name, events, repeat end, reminder, time zone), bad input explained without a download, Enter and Escape behave, light, dark and phone-width screenshots.
Not verified: importing into each calendar app by hand (Google, Apple, Outlook, Samsung); the file follows the standard and parses with a reference library, but app-specific quirks are possible. The first day of classes and the number of weeks are chosen by the student, because the portal does not publish them.

## Quick search (v0.3)

`search.js` (pure: links in, ranked pages out) + `quicksearch.js` (window, header button, keys) + `quicksearch.css`, on every CMS and LMS page that has a menu (not on the sign-in or portal-chooser pages). Ctrl+K or Cmd+K toggles it; `/` opens it unless a text field is focused; a search button sits in the header (beside the bell on the LMS, in the dark brand cell on the CMS; on phones it sits beside the menu button so nothing wraps). It is a native `<dialog>` (focus is held inside, Escape closes it, the page behind is inert) with the combobox/listbox pattern for screen readers and a live "N pages" count. Up/Down move (wrapping), Enter opens, Ctrl or Cmd+Enter opens a new tab; the page you are on is marked "You are here" and is not pre-selected. Settings > Portals > Quick search turns it off (the button and shortcuts then disappear).
What it indexes: the menu links of `aside#sideBar` (CMS) and `.main-sidebar .sidebar-menu` (LMS): their text, the heading of the submenu they sit in, and the address as the browser resolves it (so a `<base>` tag is honoured). Submenu toggles (`#...`) are skipped. Only http(s) pages on the page's own site or on bahria.edu.pk are listed (a lookalike such as `bahria.edu.pk.evil.com`, a link with a name and password in it, `javascript:`, `data:`, `blob:` and `file:` are all dropped). Ranking: page name beats related words (a small built-in list: gpa, marks, schedule, homework, syllabus, challan...) beats the submenu name; every typed word must match; one-letter typos and swapped letters are tolerated for words of five letters or more; letters typed in order from the start of a word ("prvres") match as a last resort; ties keep the menu's order. No regular expression is built from what is typed. Limits: 300 pages, 12 results (60 when nothing is typed), 80 characters typed. Nothing is stored or sent; the portal's own menu links are never changed or intercepted.
Verified: 13 unit tests (safe-link filtering including lookalike hosts, credentials and blob links; ranking, related words, typos, groups; odd input; speed; module purity), and in real Chrome with real key events: header button on both portals (one button however often the page is re-processed), Ctrl+K open/close, `/` opening it but not while typing in a field, typing, arrows, Enter navigating to the right page, Escape, no-result message, hostile menu links never listed, the portal's own links unchanged, off switch, removal when the portal is switched off, the settings preview, light/dark/phone screenshots. A catch-all check now also fails if any Campuslit panel shows "undefined", "NaN" or "null" (this caught a real bug: the attendance legend read "undefined% and above").
Not verified: the real portals' full menus beyond the saved pages (a menu built by script after load is picked up because the list is read each time the window opens); Safari.
