# Validation record

Build environment: Windows, Node.js 22.16.0. No downloaded runtime dependencies.

- Core automated tests: preference allowlisting/bounds, five-theme contrast plus custom accent extremes, system appearance, least-privilege manifest, network API absence, live content-script enable/disable, storage failure fallback, local-only storage/reset.
- Separate Chrome and Firefox builds generated by `node scripts/build.mjs`.
- JavaScript syntax checked with Node.
- Local preview server responds successfully on port 4173.
- Browser interaction checks in `scripts/browser-check.mjs` now pass: 1920, 1440, 1280, 1024, 768 and 390 px widths without horizontal overflow; bundled Inter loading; all five theme buttons; accent presets; save/reload persistence; contrast preview; reset confirmation; popup theme/enable persistence; privacy page.
- The checked local-preview flows emitted no runtime exceptions or external network requests. Desktop, wide desktop, mobile, Midnight and popup screenshots are saved under `artifacts/` and were visually inspected.
- Chrome's default sandboxed renderer failed in this managed environment. The successful local-only preview run used an isolated temporary profile and `STUDIO_BROWSER_FLAGS='["--no-sandbox"]'`. This flag is a test-harness option only, never an extension requirement or a user-browser setting.
- Firefox runtime installation and actual extension loading remain untested.
- Authenticated portal coverage remains unverified; see `COVERAGE.md`.

To run browser checks with the preview server running:

```sh
node scripts/browser-check.mjs
```

Set `STUDIO_CHROME` to another compatible Chromium executable if needed. The script keeps its isolated browser profiles and screenshots under ignored `artifacts/`. An optional `STUDIO_WS` path can point to an installed `ws` package entry point; the default uses Node's WebSocket implementation.

## Settings page and Studio (v0.3)

`npm test` (Node's runner, 15 tests) covers the theme engine without a browser: preference allow-listing, the six presets' readability, system appearance, the master/child switch rules, content-script lifecycle, storage privacy, and, for the custom theme, strict validation and name sanitising, derivation, `palette()`/`apply()`, a 2,400-palette generator sweep, a 1,500-palette fixer sweep, that good palettes are left untouched by the fixer, and that invalid custom themes are never stored. It also checks that every file the three extension pages reference exists.

`scripts/browser-check.mjs` drives headless Chrome against `npm run preview` and checks, inside the live-preview iframe (the real `cms.css`/`lms.css`): all six themes, the custom theme maker (empty state, create, typed hex with validation and 3-digit expansion, unreadable text flagged and repaired, undo, generate from a brand colour in dark mode, surprise, copying a preset, fine-tune override and reset to automatic, name safety against injected markup, accent locked for the custom theme, a custom theme staying put on a dark device, switching to a preset and back, two-click removal), sidebar navigation (one section at a time, hash in the URL, Back, real links), text size on both portals, radius, spacing, font, accent contrast, device appearance, the per-portal and master switches, plain-background and motion flags, save and reload, export (including the custom theme), import of a good file and of one with a bad colour, reset, the popup (seventh row, selecting it, keeping it when a preset is chosen, opening the Studio), five desktop widths plus 390 px with no sideways scroll, the privacy page, and no runtime exceptions or external requests.

`scripts/extension-check.mjs` (`npm run test:extension`) loads the real built extension (`dist/chrome`) into Chrome through the DevTools `Extensions.loadUnpacked` command (Chrome ignores `--load-extension` on the command line) and maps `cms.bahria.edu.pk` and `lms.bahria.edu.pk` to a local server that serves the invented sample pages in their original look. It then verifies, with the real manifest, content scripts and extension storage: the settings page runs as an extension page with its live-preview frame; the CMS (including the attendance rows and time table) and LMS are restyled by the content scripts; a custom theme designed in the settings page is written to `chrome.storage.local` on Save and applied live to the already-open portal tabs (and not before Save); the popup's master and CMS/LMS switches turn portals on and off live and keep each other consistent; choosing a preset in the popup keeps the saved custom theme and choosing the custom row brings it back; other pages pick up the saved theme on load; reset restores the default everywhere; and no tab throws a runtime exception.

Not covered: Firefox, real signed-in portals (the Studio's themes were checked by eye on saved LMS and CMS pages with a dark rose and a light mint custom theme, not automated), and the Chrome Web Store build.
